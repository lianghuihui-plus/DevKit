# 用例生成

本流程只用于用户明确要求生成、导入或维护用例。此时当前 Agent 是 Authoring Agent，不是执行协调 Agent；执行阶段“不读取原始用例”的限制不适用。

## Agent 职责

完整读取用户提供的全部输入，并使用适合其格式的可用读取能力理解内容。文本、Markdown、表格、工作簿、CSV、PDF、图片或多个文件只是信息载体；文件不是用例边界，一个输入可以形成一条或多条用例，多个输入也可以共同描述一条或多条用例。

根据实际语义识别每个可独立执行的场景。保留原始操作、条件、可选内容和预期，不因结构化而扩张、缩减或改写业务要求。只有来源内容确实无法支持稳定边界且不同选择会改变用例含义时，才向用户确认。

每条逻辑用例形成一个 draft：

- `sourceLocator`：稳定标识该用例来自哪里及其逻辑位置；重新导入同一用例时保持不变。
- `title`：便于用户识别的用例标题。
- `sourceText`：与该用例直接相关的原始内容；可以整理排版，但不能预先生成 Case Flow 或改变语义。

文件类型、行数、Sheet、章节或编号可以帮助判断，但框架不规定拆分算法。不要因为输入只有一个文件就合并全部内容，也不要因为存在多行或多个文件就机械拆分。

## 持久化

将 draft 写入一个 JSON request：

```json
{
  "cases": [
    {
      "sourceLocator": "/absolute/input.xlsx#Sheet1!R2:R4",
      "title": "账号密码登录成功",
      "sourceText": "输入有效账号和密码，点击登录，首页应正常显示。"
    }
  ]
}
```

单用例和批量用例使用同一个入口：

```bash
node <skill-root>/scripts/import-cases.js --workspace <workspace> --request-file <json-file>
```

接口只校验 draft 结构、非空内容、来源定位唯一性并完成编号、稳定标识、幂等更新和报告刷新，不判断业务边界。导入后核对返回数量和标题是否与自己的理解一致。
