# UI 自动化稳定性规则

## 何时读取

- 生成或修复任意平台 UI 自动化测试代码时读取。
- 处理点击、输入、滑动、跳转、弹窗、动画、网络请求、异步加载、列表刷新或最终断言前的稳定性问题时读取。
- 只查询某个平台的具体 API 名称时，再读取对应平台测试代码规则或官方文档。

本文件是平台无关规则。它不绑定 HarmonyOS、Android 或 iOS；各平台只负责把这些原则映射到自己的等待、查找、断言和设备操作 API。

## 核心原则

UI 自动化不能假设“上一句操作返回”就代表页面已经进入可断言状态。任何会改变 UI 状态的动作后，都必须等待下一步所需的目标状态稳定，再继续操作或断言。

这些动作包括但不限于：

- 启动应用、打开页面、返回、切换 tab 或路由跳转。
- 点击按钮、提交表单、输入文本、选择列表项、滑动页面。
- 触发网络请求、登录、刷新、分页加载、弹窗展示或弹窗关闭。
- 触发动画、遮罩、骨架屏、加载态、权限弹窗或业务确认弹窗。

禁止为了“跑快”在状态变化后立即查找、点击或断言目标控件。操作太快导致的失败，应该优先修等待策略，而不是放宽 selector、删除断言或把异常包进 `try-catch`。

## 等待目标状态

每个关键动作后，先判断下一步依赖什么状态，再等待这个状态。优先等待业务可观察目标，而不是等待固定时间。

常见目标状态：

- 页面已进入目标页面：目标页面根节点、标题、关键按钮或唯一业务文案出现。
- 页面已离开旧页面：旧页面根节点、旧按钮、旧 loading 或旧弹窗消失。
- 数据已加载完成：加载中、骨架屏、空白占位消失，目标列表、结果区或状态文本出现。
- 控件可交互：目标控件存在、可见、可点击、可输入，且没有遮罩或高层级弹窗覆盖。
- 异步流程完成：登录页消失、成功页出现、错误提示出现，或进入人工用例允许的任一终态。
- 弹窗状态明确：预期弹窗出现并可操作，或非预期阻塞弹窗已经消失/被处理。

如果存在多个合法终态，应等待共同稳定不变量。例如“离开登录页并出现首页或错误提示”，而不是只等待某一个可能不存在的页面。

## 固定等待的边界

固定 sleep 只能作为最后兜底，不应作为默认同步手段。

可以短暂固定等待的场景：

- 平台 API 没有可观察状态可等，且项目已有稳定经验。
- 动画或系统弹窗存在不可查询的短暂过渡。
- 作为轮询间隔，而不是替代最终状态判断。

即使用固定等待，也必须紧跟目标状态检查。不要写成“sleep 后直接断言通过”。

## 断言前检查

最终断言前必须确认页面处在可以断言的稳定状态。不要在跳转、提交或加载动作下一句马上断言业务结果。

推荐顺序：

```text
执行动作
-> 等待旧状态消失或新状态出现
-> 确认目标控件可见/可交互/数据已加载
-> 执行业务断言
```

如果等待超时，失败信息应能看出：

- 刚执行过的人工步骤。
- 等待的目标状态。
- 关键 selector 或可观察条件。
- 超时时间。
- 当前观察到的页面、弹窗、loading 或错误提示摘要。

## 失败修复方向

当失败表现为控件不存在、断言失败、点击无效、输入无效或页面不正确时，不要默认只改 selector。先判断是否是状态未稳定：

- 是否点击后页面还在跳转或加载。
- 是否 loading、遮罩、弹窗或动画仍覆盖目标控件。
- 是否网络请求、登录态、数据刷新还未完成。
- 是否旧页面尚未消失，导致查找命中了旧页面或空结果。
- 是否输入后页面还未接收文本、键盘/焦点状态还未稳定。

如果定位到状态未稳定，优先补目标状态等待或等待条件组合，再重跑验证。

## 平台映射

平台适配文档应把本规则映射到具体 API：

- HarmonyOS：映射到 `Driver.waitForComponent`、`assertComponentExist`、组件消失/出现判断、`waitForIdle` 的边界、dump/截图复现证据等。
- Android：可映射到 Espresso idling resource、UiAutomator wait、Compose waitUntil、adb 辅助观察等。
- iOS：可映射到 XCTest expectation、元素 `exists`/`isHittable`、predicate expectation、simctl 辅助观察等。

无论平台如何，原则都是等待“下一步所需的目标状态”，而不是等待“上一句操作执行完”。
