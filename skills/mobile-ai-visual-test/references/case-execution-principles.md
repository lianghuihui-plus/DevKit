# 用例执行原则

用例和现场事实优先；Runtime 只维护结构、生命周期、引用和技术事实，不作业务判断。

## 1. 原始语义与 Baseline Flow

1. 完整阅读原始用例后再划分条件作用域。后置的“若、如果、未出现则、跳过”等语句可以限定前面的相关操作和预期，不能只按步骤顺序逐条建模。
2. 保留“若、如果、可选、可能、无需、跳过、直到”等限定词；条件内容用分支表达，不能改成无条件步骤或检查点。
3. 原始用例允许同一事实的不同取值分别进入正常路径时，该事实建为 DECISION，分支内验证建为 CONDITIONAL CHECK；不能先为同一事实建立 REQUIRED CHECK，再用 DECISION 允许其不成立。
4. Baseline Flow 冻结原始用例语义。每条正常 END 路径必须能处置 REQUIRED CHECK，并将未进入分支的 CONDITIONAL CHECK 记为 `NOT_APPLICABLE`；不能天然依赖 `FAIL` 或 `WAIVED` 才能结束。
5. 原始用例没有要求的内容不新增为检查点；原意无法确认时记录不确定项，不自行补充产品规则。

例如“若未出现 A，则跳过 B”应建 DECISION；“未出现”进入正常 END，“出现”分支再包含 CONDITIONAL CHECK 和操作 B。

## 2. 现场适配与 Working Flow

两个及以上动作已由当前证据完整确定、步骤间不需要视觉理解、业务判断或重新规划时，优先使用 `runSequence`。动作后需要立即判断时使用 `act`；单动作后仍需按指定时机 wait 或 capture 时可以使用 `runSequence`。Runtime 自动保存动作后截图并返回最终完整 Scene，不要机械添加 capture。业务关键时刻才显式 capture，技术状态与采集不能代替业务 CHECK。

1. Baseline Flow 保存用例含义，Working Flow 表达实际路径；首次计划不冻结当前页面或导航路线。
2. 当前事实与预期不一致是新的判断输入，不自动构成终止结论；先区分必要条件无法建立与导航、临时 UI、历史状态或预想路径差异。
3. 新 Scene、动作效果、环境事实或原文理解变化时可修订 Working Flow 并记录依据，不得改写 Baseline CHECK。
4. 继续路径应安全、已授权、服务原目标、可观察验证、副作用可接受，并考虑信息增益和剩余时间。
5. 存在合理路径时自主操作、观察、重新定位、换路径或技术恢复；`recover` 非必需且不限定次数。
6. 技术成功不证明命中目标或业务成功。效果不符时核对动作、ActionRef、坐标、落点和现场，再修正或换路径；结果未知禁止自动重放，结果已知仍须确认现场适用性。

## 3. 证据与知识

1. 结论必须与 Case Flow、实际路径和已登记证据一致。截图与结构冲突、纯视觉状态或搜索覆盖不足时，继续检查或降低结论确定性，不能用缺失结构伪造业务事实。
2. `PASS` 和 `FAIL` 需要能够直接支持当前 CHECK 的可靠业务证据。技术动作失败本身不是产品 `FAIL`。
3. 查找型验证只有在已覆盖可能包含目标的范围并确认边界后，才能形成“不存在”的结论；否则披露已检查范围或使用 `INCONCLUSIVE`。
4. 现场事实不证明业务定性；知识只补充 Scene 外规则。
5. 预期不符、操作无效果或异常反复涉及外部规则时，尽早调用 `knowledge`，不等收口；无外部依赖时不机械查询。无适用候选时按现场证据判断。

## 4. CHECK 状态与最终结果

`recordResult` 记录单个 CHECK 状态，不直接提交最终 verdict：

- `PASS`：可靠 Scene 证据满足当前 CHECK 的业务预期。
- `FAIL`：当前 CHECK 适用，且可靠业务证据明确否定其预期；不得用于技术失败或证据不足。
- `INCONCLUSIVE`：已经进入当前 CHECK 的验证，但证据冲突、模糊或覆盖不足，无法可靠判断。
- `BLOCKED`：技术、环境或能力问题直接阻止当前 CHECK 继续或取得必要证据，并有有效技术事实支撑；可继续调整的页面差异不是阻塞。
- `NOT_APPLICABLE`：原始条件分支未进入，只能用于 CONDITIONAL CHECK。
- `WAIVED`：基于已有事实明确豁免 CHECK，并提交独立理由；不得替代恢复、掩盖 `FAIL` 或绕过证据不足。

正常收口调用 `finish(mode="complete")`，Runtime 忽略 `NOT_APPLICABLE` 和 `WAIVED` 后按现有 ledger 规则聚合：`FAIL` 优先于 `BLOCKED`，`BLOCKED` 优先于 `INCONCLUSIVE`，其余有效 CHECK 全部为 `PASS` 时结果为 `PASS`。全部 CHECK 都是 `NOT_APPLICABLE` 或 `WAIVED` 时仍聚合为 `PASS`，报告单独披露相应状态。

`NOT_RUN` 不是 CHECK 状态，只能通过 `finish(mode="notRun")` 形成用例级 verdict，最终结果不包含 CHECK。只有同时满足以下条件才使用：

1. 原始用例必要执行条件在当前 execution 的权限、事实和可用能力内无法建立；
2. 不存在安全、合理且仍服务原用例目标的继续路径；
3. 尚未进入相应业务 CHECK 的验证；
4. 已登记的 Scene 或技术事实足以说明无法执行的原因。

采集 Scene 不代表进入业务验证，须结合目标和实际行为判断。`NOT_RUN` 不得用于可调整的起点差异，也不得替代验证后的 `FAIL`、`BLOCKED` 或 `INCONCLUSIVE`。

## 5. 收口检查

收口前核对原始条件、实际分支、检查范围、CHECK 处置、证据和不确定项。仍有安全且有信息增益的路径时继续循环；否则使用证据可支持的状态，不为确定结论越权操作。
