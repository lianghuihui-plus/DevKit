# 用例执行原则

Case Agent 在理解、执行和收口用例时遵循以下原则。原始用例和现场事实优先，Runtime 不代替 Agent 作业务判断。

1. 完整阅读原始用例后再划分条件作用域；后置的“若、如果、未出现则、跳过”等语句可以限定前面的相关操作和预期，不能只按步骤顺序逐条建模。
2. 保留原始用例中的“若、如果、可选、可能、无需、跳过、直到”等限定词；条件内容用分支表达，不能改成无条件步骤或验证点。
3. 原始用例允许同一事实的不同取值分别进入正常路径时，该事实建为一个 DECISION，分支内的验证建为 CONDITIONAL CHECK；不能先为同一业务事实建立 REQUIRED CHECK，再用 DECISION 允许其不成立。
4. 提交 Case Flow 前逐条检查原始用例允许的正常 END 路径；每条路径都必须能让 REQUIRED CHECK 正常得到验证，或让未进入分支的 CONDITIONAL CHECK 记为 NOT_APPLICABLE，不能天然依赖 FAIL 或 WAIVED 才能收口。
5. 原始用例没有要求的内容，不新增为验证点；原意无法确认时记录为不确定项，不自行补充产品规则。
6. 查找目标时，在可能包含目标的列表、横滑区域、分页、Tab 或折叠区域中持续探索，直到找到目标或确认到达边界；一次未看到或一次滑动无效，不能作为目标不存在或不可达的依据。
7. 操作无效、结果异常或证据冲突时，先核对执行路径、动作落点或轨迹、最新 Scene、观察范围和环境差异，再决定下一步。
8. 现场与 Case Flow 不一致时可以调整流程；每次调整都要记录触发调整的新事实或理解变化。
9. 提交结果前，逐项核对原始用例中的条件、可选内容和验证范围，确保 Case Flow、实际路径、证据和结论一致。

例如“预期出现 A；操作 B；若未出现 A，则跳过 B 并正常结束”应先建“是否出现 A”的 DECISION。“未出现”直接连到正常 END；“出现”分支再包含验证 A 内容的 CONDITIONAL CHECK、操作 B 和后续条件检查。
