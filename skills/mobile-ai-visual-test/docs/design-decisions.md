# mobile-ai-visual-test 关键设计决策

本文只记录需要长期保持的选择、原因和影响。当前行为、模块边界和数据流以 [`architecture.md`](architecture.md) 为准。

## D1：Agent 按业务阶段分工

- 决策：Authoring Agent 判断输入中的逻辑用例边界；执行协调 Agent 只负责编排；Case Agent 是 execution 内唯一业务理解者，并自主生成和修订 Case Flow。
- 原因：格式规则不能可靠表达用例边界，协调层重复理解原文会增加耗时并造成语义降级。
- 影响：Case Flow 同时承担用例理解和执行导航；调整计划或检查点只需记录理由，不需要协调层审批。

## D2：Handoff 只绑定身份与所有权

- 决策：Handoff 直接交付 execution、原文、现场摘要和预绑定 Runtime Client；执行协调 Agent 不转读或转述 Case Agent 上下文。
- 原因：由协调层搬运业务内容会破坏角色隔离，并让协调耗时随用例复杂度增长。
- 影响：Loader 必须原样执行；dispatch 只表达 `PREPARED / CONSUMED / REPLACED` 和 sequence，不虚构 Agent 运行状态或超时租约。

## D3：薄 Agent-facing，厚确定性框架

- 决策：Agent 面对少量语义能力，Translator 注入绑定信息，Runtime 负责严格契约、事务、证据和状态机；调用与恢复文档按角色、方法和错误渐进披露。
- 原因：直接暴露内部 ID、状态和完整 Schema 会占用 Agent 注意力，也容易导致参数猜测；一次加载全部文档同样会挤占业务上下文。
- 影响：响应提供动态事实和精确 `documentationRef`；框架能力是首选路径，但异常时 Agent 仍可在授权范围内使用其他工具，随后回到框架核验。

## D4：多种证据并列，动作只返回事实

- 决策：截图、控件树、知识和动作落点是并列能力；Adapter 与 Runtime 陈述实际采集和投递事实，不判断业务效果。
- 原因：权限弹窗、Toast、遮罩、动画和产品差异可能不在控件树中，而设备层无法证明 Agent 选择了正确目标。
- 影响：视觉结论必须登记图片事实；操作异常时 Case Agent 检查标注落点和当前 Scene，自行决定是否纠正、重试或收口。

## D5：事实追加保存，只执行当前格式

- 决策：原文、Scene、动作、知识、Case Flow revisions、结果与完成绑定采用不可变或追加式记录；新 Runtime 只写和执行当前 schema。
- 原因：报告必须还原当时现场，长期读写旧格式会把兼容分支扩散到整个框架。
- 影响：旧工作空间可创建新 Run；旧 execution 不迁移、不补写，历史 Case Model 仅在 Reader 支持范围内只读展示。

## D6：业务终态、资源释放和报告发布分离

- 决策：Execution 收口、平台资源释放、Batch 终态和报告发布分别持久化；不同平台可在同一工作空间并行，共享报告通过发布锁串行生成。
- 原因：展示失败不代表测试仍在运行，跨平台设备操作也不应被工作空间级派生产物互相阻塞。
- 影响：报告失败不会把业务改回等待态；发布成功必须覆盖冻结目标；真实设备、Appium/WDA 和同平台并发继续受所有权层保护。

## D7：破坏性准备和平台资源必须有明确授权与归属

- 决策：Case Agent 只表达目标 App 的期望状态，框架负责平台等价实现、制品匹配和结果校验；Session 与平台服务按 Batch 所有权管理。
- 原因：三端接口应一致，但清数据、卸载重装和服务回收都可能产生不可逆影响。
- 影响：缺少有效制品或无法证明资源归属时先失败；明确失败只做受控恢复，结果未知不重放，归属不明的资源不自动清理。
