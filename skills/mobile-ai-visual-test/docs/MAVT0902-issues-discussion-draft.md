## 1. 列表搜索不完整导致错误结论

### 现象与证据

- 019 的一次执行从列表底部附近开始，没有形成完整列表覆盖证据就结束搜索。
- 019 的另一次执行只向反方向滑动两次，并通过卡片位置推测到达顶部，但没有可靠的边界证据。
- 021 初始截图中首个卡片已经被裁切，说明起点位于列表中部；重新点击已选中的标签没有重置滚动位置。
- 021 随后只向列表底部搜索，多次滑动到底后直接判定找不到，初始位置上方从未被检查。
- 020 刚完成作品复制，新作品可能位于 021 初始位置上方，因此 021 的 `BLOCKED` 缺少完整搜索证据。

### 根因

- Case Agent 只能看到当前页面及通用滑动能力，不知道列表的已覆盖范围、未覆盖方向和边界是否已经确认。
- Agent 容易把“当前方向没有找到”错误等同于“完整列表不存在”。
- 当前能力协议没有为“不存在”这一负向结论提供可验证的列表覆盖依据。

### 已确认的设计取舍

- 不设置“必须滑动 N 次”“必须先向某个方向滑动”等固定导航规则，保留 Agent 选择搜索路径的自由度。
- 不使用动态 Prompt；不根据实时状态拼接额外自然语言提示，避免增加 Prompt 管理和执行链复杂度。
- 不采用固定 30% 重叠；固定比例在不同卡片尺寸和列表密度下都不稳定。
- 采用自适应衔接，目标是相邻观察至少保留一个可识别的共享列表项，而不是强制某个百分比。
- 主要防线必须发生在 Agent 作出结论之前；`finish` 阶段的校验只作为兜底，不能依赖驳回后再次搜索。

### 拟定方案

Runtime 在标准 `observe` 或滑动操作返回值中持续提供固定结构的滚动上下文；这是能力协议的一部分，不是动态 Prompt：

```json
{
  "scrollContext": {
    "startPosition": "UNKNOWN",
    "reachedStart": false,
    "reachedEnd": true,
    "searchedAbove": false,
    "searchedBelow": true,
    "unexploredDirections": ["UP"],
    "absenceConclusionSupported": false
  }
}
```

实现原则：

- Runtime 根据相邻页面的共享锚点、内容位移以及滑动后无位移现象维护边界和覆盖状态。
- Agent 每次决策前都能从普通能力响应中看到尚未搜索的方向，因此可在同一执行循环内继续搜索，不需要先提交错误结论。
- 标签切换、刷新、复制、删除或列表内容明显变化后，原覆盖记录必须失效，防止使用过期证据。
- 当起点未知时，只有覆盖初始位置两侧，或者从一个已确认边界连续搜索到另一个已确认边界，才能支持“完整列表中不存在”。
- 若证据不足，只能表达“已检查区域未找到”，不能据此把缺失目标判为 `FAIL` 或 `BLOCKED`。
- 在固定 Case Agent 协议中一次性说明 `scrollContext` 字段语义；运行中不追加动态自然语言提示。
- `finish` 仍校验负向结论是否引用有效覆盖证据，仅处理模型忽略状态等残余异常。

### 效率判断

- 当前通用滑动距离大约只覆盖半屏，固定 30% 重叠不一定比现状更慢，但不是最优抽象。
- 使用“至少一个共享锚点”的自适应衔接，可在卡片较大时减少重叠，在识别不稳定时自动缩短步幅。
- 前置暴露未覆盖方向可避免错误 `finish` 后返工，正常路径不会新增一轮 Agent 推理。

### 修复时预计涉及

- `scripts/case-runtime/capability-catalog.js`
- `scripts/case-runtime/scene-service.js`
- `scripts/lib/layout-observation.js`
- `prompts/case-agent.md`（仅固定协议说明，不做动态 Prompt）
- Runtime 的 `finish` 结果完整性校验

### 修复设计已收敛

- 边界使用 `UNKNOWN`、`PROBABLE`、`CONFIRMED` 三级置信度，只有 `CONFIRMED` 可支持不存在结论。
- 覆盖状态绑定 generation、页面上下文、滚动容器以及标签/筛选等列表外状态。
- 第一阶段只支持布局树可识别的单层垂直列表；横向、嵌套和纯视觉列表不伪报完整覆盖。
- 详细契约、算法边界和测试方案见 `docs/MAVT0902-fix-design.md`。

## 2. 系统权限弹窗点击无效

### 已完成的排查

- Agent 请求的视觉坐标约为 `(1278, 671)`，在作为坐标依据的 `2232×1008` 截图中位于“允许”按钮区域；这只能证明目标选择合理，不能证明设备实际触点落在该位置。
- 当前执行的截图和系统窗口记录均为 `2232×1008`，暂未发现简单的截图尺寸缩放错误，但仍不能排除输入注入在横屏或系统窗口中的坐标转换问题。
- `scripts/platform/adapters/harmony/atoms/tap.sh` 把 HDC 点击命令成功发送视为操作成功，并不能证明系统弹窗实际消费了点击。
- 返回的 `executedPoint` 是请求坐标的回显，不是设备反馈；坐标审计显示 `MATCHED` 只能证明请求和回显一致。
- 当前截图没有保存真实触点标记，Case Agent 只能从弹窗保持不变判断点击无效，不能判断触点实际偏向了哪里；如果人工观察到触点向左偏移，该信息目前没有进入证据链。
- 系统权限弹窗不属于 App 自身窗口，按应用包过滤的布局抓取会得到语义为空的根节点。
- `scripts/platform/adapters/harmony/atoms/dump-tree.sh` 只判断文件非空，没有在语义树为空时继续尝试无过滤抓取。
- 普通 App 点击以及部分相机、麦克风权限点击能够成功，说明底层 HDC 点击能力并非整体失效。

### 已确认的框架根因

- Runtime 把“底层命令正常退出”错误提升成“操作成功”，混淆了命令投递、设备执行、界面效果和业务预期四种不同语义。
- 下层适配器应返回可验证的执行事实；无法观测真实触点或界面效果时必须明确返回 `UNKNOWN` 或 `UNVERIFIED`，不能构造成功事实。
- Runtime 不应替 Agent 判断业务步骤成功；它应把实际操作结果和证据交给 Agent，由 Agent 对照用例预期判断是否达到业务目标。
- 系统权限弹窗不是独立根因，而是最明显地暴露了这项通用 Runtime 设计缺陷。

### 已确认的结果模型方向

操作生命周期、命令结果和可观察效果必须分层表达；以下结构仅用于说明语义，具体字段名在实现时结合现有契约确定：

```json
{
  "operationStatus": "COMPLETED",
  "command": {
    "status": "ACCEPTED",
    "requestedPoint": {"x": 1278, "y": 671}
  },
  "deviceExecution": {
    "status": "UNVERIFIED",
    "actualTouchPoint": null
  },
  "observedEffect": {
    "status": "UNCHANGED",
    "evidence": ["beforeScreenshot", "afterScreenshot"]
  }
}
```

- `operationStatus: COMPLETED` 只表示 Runtime 已完成本次操作记录，不表示点击生效。
- `command.status: ACCEPTED` 只表示 HDC 接受并正常执行命令调用。
- `deviceExecution` 描述真实设备操作；没有设备反馈时保持 `UNVERIFIED`。
- `observedEffect` 只描述布局、截图、前台窗口或权限状态的实际变化，不替 Agent 推导业务结论。
- Case Agent 应看到这些分层事实，而不是单一的 `ok: true` 或 `SUCCEEDED`。

### 最终讨论结论

- 优先统一改造通用 Action Result 和操作状态语义，而不是只给系统弹窗打补丁。
- 将 HarmonyOS 当前的 `executedPoint` 改为 `requestedPoint` 或 `dispatchedPoint`，或标记为 `UNVERIFIED_REQUEST_ECHO`，禁止将请求回显解释为真实触点。
- 为点击、滑动、长按、输入等操作分别定义可验证的设备执行事实和可观察效果；无法验证时如实返回未知。
- 不增加系统弹窗专用点击能力；系统弹窗和普通控件统一使用上述通用结果契约处理。
- 命令正常退出但界面无变化时，只能记录“命令已接受、未观察到效果”，不能向 Agent 返回操作成功。
- Agent 根据实际结果和用例预期判断业务是否成功，Runtime 不替 Agent 推导业务结论。

### 暂缓项：坐标偏移

- 视觉点击目前由 Agent 直接提供归一化单点，Runtime 只做线性像素换算，并没有根据按钮边界计算中心点。
- 本次 `(1278, 671)` 与截图中“允许”操作区中心非常接近，现有证据不能证明归一化换算公式存在错误。
- 视觉操作把 `targetBounds` 记录为整个屏幕，且 HarmonyOS 不返回真实触点，因此框架目前无法验证点是否位于控件中心，也无法定位设备注入阶段可能存在的偏移。
- 本轮修复暂不处理坐标选择、目标区域建模和真实触点诊断；后续出现更充分证据时另行处理，不在本问题中加入经验性坐标补偿。

## 3. 横屏状态下重启 App

### 已完成的排查

- 039 的 `recovery-0001.json` 明确记录设备形态为 `triplefold`、请求方向为 `portrait`，但方向归一化策略只适用于 `phone`，因此被标记为 `SKIPPED`。
- 重启前为横屏，启动后仍为横屏，说明问题不是页面偶发渲染，而是启动方向策略没有覆盖当前设备形态。
- `scripts/lib/startup-display.js` 的默认方向策略仅适用于 `phone`。
- 040、041 很可能是 039 恢复后遗留横屏状态造成的级联异常。

### 最终讨论结论

- 不把 `triplefold` 等具体设备类型加入手机白名单，也不依赖静态 `deviceFormFactor` 决定启动方向策略。
- 每次冷启动或 `restartApp` 前读取当前有效屏幕的宽高，根据运行时显示形态判断为 `phone-like` 或 `tablet-like`。
- 使用与方向无关的长短边比例作为轻量判断依据：`max(width, height) / min(width, height)`；阈值集中定义，不散落在调用代码中。
- `phone-like` 复用现有手机策略：启动前恢复竖屏并验证，启动 App 后再次检查，必要时再纠正一次。
- `tablet-like` 复用现有平板策略：保持当前方向启动，不执行手机竖屏归一化。
- 当前三折叠设备的有效屏幕为 `2232 x 1008`，长短边比例约为 `2.21`，应判断为 `phone-like` 并执行竖屏启动策略。
- 启动结果记录静态设备类型、运行时宽高、比例、最终显示形态、选择的策略及启动后方向，便于追溯判断依据。
- 启动后未达到所选策略要求时明确返回恢复失败，不能把策略跳过或方向未验证汇总为成功。

### 独立风险

- 杀 App 会丢失暖会话中的深层业务状态；这与显示形态判断是两个问题，不纳入本次方向策略修复。

## 4. 长按支持异常

### 已完成的排查

- 006 要求长按 5 秒，但实际操作记录只有 `800 ms`。
- `scripts/platform/adapters/harmony/atoms/long-press.sh` 的默认时长是 `800 ms`。
- `scripts/case-runtime/capability-catalog.js` 在构造视觉操作时保留了手势和坐标，但丢失了 `durationMs`。
- 元素能力路径也没有完整传递长按时长。
- Device Port 已支持 `observationPolicy.duringActionAtMs`，但能力协议没有让 Agent 清楚地使用它。
- “松开发送”等状态只在按住期间出现，仅在动作结束后截图无法验证长按过程。

### 最终讨论结论

长按请求应完整传递时长，并允许在按住期间取证：

```json
{
  "visual": {
    "gesture": "longPress",
    "point": [0.55, 0.92],
    "durationMs": 5000
  },
  "observationPolicy": {
    "duringActionAtMs": 4000
  }
}
```

- 这是确定的参数透传 bug：视觉长按重建 Action 时未复制 `visual.durationMs`，控件长按也未从 `input.durationMs` 读取时长。
- 视觉长按和控件长按只是在目标定位方式上不同，最终必须生成同一种包含坐标和 `durationMs` 的底层 `longPress` Action。
- Case Runtime 的长按请求必须明确携带正整数 `durationMs`，不再静默回退到 `800 ms`；缺少或非法时长时在执行前返回请求错误。
- 固定接口说明同时向 Agent 暴露视觉长按和控件长按的时长输入格式，不使用动态 Prompt。
- 操作结果按第 2 个问题确定的通用结果语义，分别记录请求时长、命令投递结果、可验证的实际耗时和可观察效果，不能只返回 `ok: true`。
- 对需要验证按住态的用例，使用现有 `observationPolicy.duringActionAtMs` 在释放前取证，并校验取证时间位于长按持续时间内。
- 006 使用 `durationMs: 5000`，在约第 `4000 ms` 保存“松开发送”等按住态，释放后再观察语音消息是否发送。
- 历史执行只保存了 Runtime 解析后的 Action，无法确认当时 Agent 原始请求是否包含 `5000 ms`；但现有代码可以确定，即使传入也会在映射过程中丢失。
- HarmonyOS 真机验证确认静止的 `DOWN -> 等待 -> UP` 序列不能稳定触发长按；底层改用 `uinput -T -m x y moveX y -k keepMs smoothMs`，在目标附近微移 1 像素并持续产生 MOVE，不引入 SDK、Driver 或测试 HAP。
- `smoothMs = min(durationMs, 1000)`，`keepMs = durationMs - smoothMs`，两段之和保持请求时长；受 HDC 参数上限约束，HarmonyOS 长按支持 `1..61000 ms`。
